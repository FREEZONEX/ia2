# D11：读侧只认签名有效的事件与样本（设计，未实现）

> **独立修复副本（P1，2026-10-28）：** §1 和 §7 按 D01 订正了"伪造 `verified` 需要同时偷到两把密钥"的说法，并在 §7 加了信任矩阵；设计的其余部分没有动，**D11 仍然没有实现**（没有签名、密钥、信封、部署）。

## 1 要堵的洞

`verified` 的两个输入——桥写的 `accepted` 事件、读侧看到的反馈样本——都经过 Tier0 的、没有逐主题密钥 ACL 的主题（`tier0-acceptance-20261022/RESULT.md`）。W1 的修复让验证器不再信请求记录，但：

| 谁能写 Tier0 的事件 / 样本主题 | 能做什么 |
|---|---|
| 只伪造 `accepted` 事件 | 编一个目标值和扫描时钟标记，配上真实的、恰好等于它的反馈 → `verified` |
| 只伪造样本 | 配上真实的 `accepted` 事件，在 `post_scan_us` 之后编一个等于目标的新鲜样本 → `verified` |
| 两个都伪造 | 任意 `verified`，设备根本没动 |

**所以只签事件不够，样本也必须签**：否则攻击者只要伪造那一半。两个都签之后，是这样（P1 的 D01 订正了这里原先"伪造 `verified` 需要同时偷到两把密钥"的说法，它是错的）：**事件与样本分别认证来源，并依赖各自签名者正确报告事实；任一事实来源出错，结合另一端真实且匹配的记录，也可能形成错误 `verified`。独立密钥不是双人授权，`verified` 仍不证明物理效果。** 每个事实签名者（桥、采样器）都是各自那部分事实的**正确性信任点**；签名有效只说明"是它说的、没被改"，不说明"说的是对的"。逐种情形见 §7 的信任矩阵。

## 3 格式

沿用 D10 的做法：**签精确字节，先验签后解析，域前缀防串用**。

**事件**（`trace.jsonl` 里每一行，包括 `action_status`、`conflict_notice`、`reconcile_note`、`bridge_notice`）：

```json
{"v":"ia2.event/v0","key_id":"b1","payload":"<事件 JSON 文本，作为字符串>","sig":"<hex>",
 "hint":{"kind":"action_status","action_id":"…","event_id":"…"}}
sig = HMAC-SHA256(event_key[key_id], b"ia2.event/v0\n" + payload 的 UTF-8 字节)
```

- `payload` 就是现在的事件，里面照旧带 `journal_seq` / `journal_hash`（于是**锚也被签名保护**，W2 的外部锚不能再被改写）。
- `hint` **不可信**，只为让 Tier0 能按 `action_id` 等字段检索（payload 是字符串，Tier0 看不进去）。验证器**不用** hint，且 hint 与 payload 不一致的事件整条忽略。

**样本**：

```json
{"v":"ia2.sample/v0","key_id":"s1","payload":"<样本 JSON 文本>","sig":"<hex>","hint":{"event_id":"…","native_runtime_id":"…"}}
sig = HMAC-SHA256(sample_key[key_id], b"ia2.sample/v0\n" + payload 的 UTF-8 字节)
```

三种签名各用自己的**域前缀和密钥**：请求 `ia2.control/v0\n`、事件 `ia2.event/v0\n`、样本 `ia2.sample/v0\n`——一种的签名换到另一种上必然不通过。前缀写进 `contract_vocab.json`，桥与验证器都从那里读（仍然只共享这一个文件）。

## 4 密钥

| 角色 | 谁签 | 谁验 | 存在哪些主机 |
|---|---|---|---|
| 请求（已有，D2/D10） | 控制工具集 | 桥 | 工具集主机、桥主机 |
| **事件（新）** | 桥 | 读侧（验证器） | 桥主机、读侧主机 |
| **样本（新）** | 采样器 | 读侧 | 采样器主机、读侧主机 |

- 三把互相独立。**读侧主机和工具集主机在 1b 里是同一个**（`get_action_status` 在 Agent 面工具集里算 `verified`），所以这个主机本来就持有请求密钥，新增的两把没有扩大信任的人群——但它被攻破就能伪造一切（见 §7）。
- 文件格式同请求密钥：`{key_id: {secret_hex, not_before_ms, not_after_ms}}`，**0600**（W7 的检查直接复用）。桥、采样器各有一个**签名密钥文件**（可以放几把，用最新的有效的那把签）；验证器持有**验证密钥**。
- **轮换**：窗口重叠。验证时看的是**事件自己的时间戳**（`observed_at_ms` / `collected_at_ms`，在签名里）是否落在那把密钥的窗口里，不是验证的此刻——旧事件在密钥过期后仍然可验。
- **撤销**：验证器配置里一份 `revoked_key_ids`。已泄露的密钥即使窗口没过也被拒。这是必要的，因为持有过期密钥的人可以倒填时间戳。

## 5 验证器怎么变

输入从「事件列表、样本列表」变成「信封列表」，先过一道门：

| # | 规则 |
|---|---|
| V1 | 信封恰有字段 `v`、`key_id`、`payload`、`sig`（可选 `hint`）；`v` 与种类相符（事件 / 样本） |
| V2 | `key_id` 在该角色的验证密钥里、没被撤销；`sig` 用 `compare_digest` 核对（先于任何解析） |
| V3 | 解析 payload（严格 JSON，同桥）；`payload` 的时间戳落在这把密钥的窗口里 |
| V4 | `hint` 若存在必须与 payload 一致，否则整条忽略 |
| V5 | 事件：`schema == ia2.control/v0` 且 `kind` 已知；样本：`schema == ia2.sample/lab`（生产名另定） |
| V6 | 不通过的信封**计数**并在结果里报告（`rejected_envelopes`），但不影响其他事件 |

通过门之后的规则**不变**（§7 的各条、第一条桥事件为准等）。`derive(...)` 新增参数 `event_keys`、`sample_keys`、`revoked`；**不给密钥就拒绝工作**（没有「宽松模式」，D14）。

## 7 这样还是防不住的

**信任矩阵（设计级，P1 的 D01）。** 只用两个前提：这一端的**认证是否通过**（来源与完整性），和它报告的**事实是否正确**。验证器能检查前者，检查不了后者，所以"签名有效但事实错误"的输入它**识别不了**，这是本设计的局限，不是待修的缺陷：

| 事件：认证 / 事实 | 样本：认证 / 事实 | 读侧会怎样 | 得到的 `verified` |
|---|---|---|---|
| 通过 / 正确 | 通过 / 正确 | 可以 `verified` | 可信，等级 L2（仍不证明线上送达与物理效果） |
| 通过 / 正确 | 通过 / **错误**（采样器被攻破，或报告有误） | 可以 `verified` | **不可信**，读侧无法识别 |
| 通过 / **错误**（桥被攻破，或报告有误；例如设备本来就在该值） | 通过 / 正确 | 可以 `verified` | **不可信**，读侧无法识别 |
| 通过 / **错误** | 通过 / **错误** | 可以 `verified` | **不可信**，读侧无法识别 |
| 任一端认证不通过 | — | 这一条被忽略 → `requested` / `unknown` | 没有 `verified` |

所以**独立密钥不是双人授权**：错误的 `verified` 不需要同时失去两把密钥，一个签名者出错，再碰上另一端真实且恰好匹配的记录就够了。**不作保证的事**：验证器识别"签名有效但事实错误"的输入；`verified` 证明物理效果；两把密钥互相制衡。

- **读侧 / 工具集主机被攻破**：它持有三把密钥（请求、事件、样本的验证），能伪造一切。HMAC 是对称的，这点没法靠 HMAC 解决（D13）。
- **桥主机被攻破**：本来就能直接写 IA2；也能写出任意 `accepted` 事件，只要反馈真实且恰好等于它的目标值（设备本来就在这个值）就能得到 `verified`。
- **采样器被攻破（或报告有误）**：能伪造反馈。桥每写一次都会留下真实的 `accepted` 事件，所以只要有一条这样的事件，配上伪造的新鲜样本就能凑出 `verified`——被伪造的是反馈，**不需要桥的密钥**。
- **删除、截断、延迟事件或样本**：读侧看到的只会更少 → `requested` / `unknown`。这是安全的失败方向，但是可用性问题。
- **重放真实的旧事件**：事件带 `action_id`，样本带 `native_runtime_id` + `scan_timestamp_us`，旧样本早于 `post_scan_us`，不能满足窗口；所以重放不能造出新状态。
- **时钟**：密钥窗口用的是桥 / 采样器自己写进签名里的时间戳；被偷走的旧密钥可以倒填。靠撤销名单。

**要改：** `bridge/trace.py`（写信封、启动时拆信封读锚）、`bridge/main.py`（要求事件密钥，退出码 2 之类）、`bridge/auth.py`（密钥加载可复用）、`lab/verifier.py`（V1–V6）、`lab/sampler.py`（签名）、`lab/standin.py`/`harness.py`（读 trace 要拆信封）、`contract_vocab.json`（域前缀）、所有直接读 trace 行的测试（约 10 处）。

**新的测试：**
- 单元：事件 / 样本各自的伪造变体——无签名、错签名、篡改 payload 保留签名、未知 `key_id`、**用请求密钥签的事件**（角色混用）、**用事件密钥签的样本**、hint 与 payload 不一致、密钥窗口外、撤销、过期密钥签的旧事件仍可验；信封解析的畸形输入（沿用 `robustness_cases` 的方式）。
- 用例（建议新增，P0）：**F6 伪造事件**——测试夹具扮演「能写 Tier0 的人」，往 trace 里追加一条编好的 `accepted`；验证器给 `requested`，结果里 `rejected_envelopes` ≥ 1。**F7 伪造样本**——真实的 `accepted` + 伪造的新鲜样本 → 不 `verified`。**F8 两者都伪造** → 不 `verified`。**A1 等现有用例不变**（它们走签名路径）。
- 变异：验证器跳过验签；用错角色的密钥；信任 hint；忽略撤销；用验证时刻而非事件时刻查密钥窗口——每个都必须被某个测试抓到。
