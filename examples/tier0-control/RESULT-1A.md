## 5 WP6 对账程序

[`tools/reconcile_report.py`](tools/reconcile_report.py) 只读文件，不导入桥的任何代码。分类按 CONTRACT §8.3 加上 R3T1 的教训：

- `consistent`：`/audit` 恰有一条、与 intent 和桥收到的答复一致，设备在同一实例运行时收到了应用的值（或有理由没收到：IA2 说未送达、设备已持有该值、设备收到请求却没应答、一个输出周期内被确认在其后应用的新值或实例重启替换、设备日志证明从写入到被替换（或完整日志结束）之间没有可用链路；2026-10-29 审核修复后的规则见 §7，复核后的修复见 §8）。
- `executed_unaudited`：归档覆盖了这次写入却没有条目，设备收到了值，桥没收到 HTTP 答复——客户端断开后执行、IA2 漏记（CONTRACT §11.5）。
- `not_sent` / `no_effect_no_entry`：没有条目、设备无效果；代理日志证明没发出，或发出后没有答复（R1 / R3）。
- `uncheckable_restart` / `uncheckable_turnover`：归档没能在该实例里、无缺口地看到它，且有实例重启或环回绕的证据。
- `uncheckable_archive` / `uncheckable_device_log`（审核修复新增）：归档停止看这个实例却没有它结束的证据；或判断需要设备日志的覆盖而日志没有覆盖。二者让结论成为 `INCOMPLETE`（退出码 2），不是 `CLEAN`。
- `uncheckable_order`（复核修复新增）：值没在本实例确定运行时送达，而结论取决于证据定不了的先后：另一个值与它先后未知，或设备收到它时不知道是哪个实例在运行（没有生命周期记录）。同样是 `INCOMPLETE`。
- `unexplained`：其余一切（条目与 intent 不符、两条条目、有 HTTP 答复却无条目、设备收到却无条目而桥有答复、应用的值始终没到设备、同一标签两次 POST）。

另列：没有 intent 能解释的审计条目（**不明写入**），没有任何完整应用先后或合法交接能解释的设备写入（**无法解释的设备写入**；程序自赋值与安全态的值除外），以及只有部分可能性可解释或超出搜索预算的设备写入（`unchecked_device_writes`，证据缺口）。前两者都为空、journal 哈希链完好、且没有上述证据缺口时才是 `CLEAN`。当前单元向量 69 项，`tools/check_reconcile_mutations.py` 的 64 个人为改坏的版本都被断言抓到（§9）。历史记录：第一轮复核修复后 62 项 / 56 个（`evidence/rereview-20261029/`），审核修复后 48 项 / 39 个（`evidence/reconcile-mutations/`），最早 22 项 / 16 个（`evidence/reconcile-mutations.log`）。

局限：归档条目没有 ID，相邻两条逐字相同的条目算一条（重发靠代理日志的 POST 计数查）；设备日志与生命周期文件是实验室才有的来源，生产环境里只有 journal 与 `/audit`，`executed_unaudited` 与 `no_effect_no_entry` 分不开。
